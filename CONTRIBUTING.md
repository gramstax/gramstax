# Contributing to Gramstax

Thanks for wanting to contribute. Gramstax is a Bun + TypeScript + Nx monorepo:
the core framework (`packages/gramstax`), the scaffolding CLI
(`packages/create-gramstax`), and the independently published packages
`@gramstax/lmdb` (`packages/lmdb`) and `@gramstax/worker-thread`
(`packages/worker-thread`). Skills live in `skills/`, the docs site in
`docs-site/`, and sample projects in `example/`.

Please read the [Code of Conduct](CODE_OF_CONDUCT.md) first. By participating
you agree to abide by it.

## Ways to contribute

- **Report a bug** — open an issue with the bug report template. A minimal
  reproduction is the single most useful thing you can include.
- **Suggest a feature** — open an issue with the feature request template
  first and discuss it before writing code. Pull requests are not a
  feature-request surface: an unsolicited large feature PR is likely to be
  closed. Small, well-scoped improvements are welcome once the direction is
  agreed in the issue.
- **Improve the docs** — fixes to guides, references, and examples are
  always welcome.
- **Fix a bug** — pick an issue labelled `ready-for-agent` (fully specified)
  or `ready-for-human` (needs a person at the keyboard). Comment on the issue
  before starting so work is not duplicated.

Questions go in an issue too — use the docs first
(https://gramstax.mintlify.site/) and say what you already checked.

## Development setup

- Install [Bun](https://bun.sh) (CI currently pins Bun 1.4.5).
- `bun install` from the repository root.
- Commands are run from the repository root unless noted; see `AGENTS.md`
  for the full list.

## Before you open a pull request

- Run the gates: `bun run ci:test:packages` (typecheck + lint + package
  tests), or `bun run prepush` (the full check plus build). A PR that fails
  these will not be merged.
- Add or extend tests for every behavior change. Tests use `bun:test`
  (`describe`, `it`, `expect`); there is no vitest or jest.
- Keep the change focused and small. One concern per PR; refactor-only
  changes go in their own PR.
- Do not bump package versions, edit `CHANGELOG.md`, or hand-edit the
  generated API reference in `docs-site/reference/` — releases and the skill
  metadata version sync are done by maintainers in CI.
- Do not hand-edit `docs-site/config/navigation.json` either; it is
  regenerated by `bun run build:docs`.

## Style

- Formatting and linting are enforced by Biome: 2-space indentation, no
  semicolons, `bracketSpacing: false`. Run `bun run lint` and
  `bun run format` before pushing. Prefer backticks for strings, matching
  the surrounding file.
- Use ESM `import`/`export` (the repo is `type: module`) and `node:` prefixes
  for built-in modules. Use `import type` for type-only imports.
- `strict: true` and `noUncheckedIndexedAccess: true` are on. Prefer precise
  types over `any`; use `unknown` where the shape is genuinely open.
- Never use `@ts-ignore` or `@ts-expect-error` to hide an error — fix it.
- Keep public API names descriptive. Add new public exports to the package
  barrel (`packages/gramstax/src/index.ts` for the core package).

## Commits

Use conventional commits with a scope, for example:

- `fix(gramstax): ...`
- `feat(lmdb): ...`
- `docs: ...`
- `test(gramstax): ...`
- `ci: ...`

Write the subject in the imperative mood and explain the *why* in the body
when it is not obvious from the diff.

## Pull request process

1. Fork the repo and create a branch from `main`.
2. Make the change, add tests, run the gates above.
3. Open the PR against `main` with a clear description: what changed, why,
   and which issue it closes (if any). Fill in the PR template checklist.
4. A maintainer triages it with the labels in `docs/agents/triage-labels.md`
   (`needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`,
   `wontfix`) and reviews it. Expect review comments; address them and
   re-run the gates.

## Releases

Releases are cut by maintainers with `nx release`. Do not include version
bumps, tags, or changelogs in a contribution PR.
