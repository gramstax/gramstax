# Gramstax Repo Superplan

Plan lifecycle for the Gramstax framework monorepo. This is the maintainer-facing front end to the generic `superplan` and `superbuild` skills:

- `superplan` supplies the executable phase structure: acceptance criteria, estimates, TDD tasks, Definition of Done, and CHECKPOINTs.
- `superbuild` supplies execution discipline. This skill hands off to it; it does not replace it.
- `grill-me` supplies the interview method: a design tree, a frontier, rounds, and a recommended answer for every question.

The result is a plan that lives in `plans/`, matches Gramstax's package boundaries, and can be executed by `superbuild` without re-planning.

> **Scope:** use this skill only when the repository contains the framework packages (`packages/gramstax`, `packages/create-gramstax`, `packages/lmdb`, `packages/worker-thread`). For an app that depends on Gramstax and has `gramstax.config.ts`, use `skills/gramstax-superplan` instead. Do not plan edits to installed `node_modules` here.

## When to Apply

- Starting a new Gramstax feature, refactor, migration, or release task.
- Changing scope, architecture, phases, or tests in a plan that is already written.
- Reviewing a plan before execution.
- Resuming a paused or compacted implementation.
- Reconciling what was actually built with what the plan said.
- Preparing a superbuild handoff or an execution report.

Do **not** use this skill for a one-line fix, a known-path edit, or work that already has an approved, current plan. Execute that work directly or use `superbuild`.

## Modes

| Mode | Trigger | Output |
| --- | --- | --- |
| **CREATE** | No plan exists | `plans/NNN-feature-slug/plan.md` |
| **REFINE** | Scope, design, task, or verification changes | Minimal plan edits + change-log entry |
| **REVIEW** | Plan needs an audit | Findings table; rewrite only when asked |
| **RESUME** | Work was paused or compacted | Current state, next phase, blockers, resume prompt |
| **RECONCILE** | Execution drifted from the plan | Corrected statuses, deviations, re-sequenced phases |
| **HANDOFF** | Plan is ready to execute | `superbuild` prompt with scope and gates |

## Hard Rules

1. **Facts are your job; decisions are the user's.** Read the repository or dispatch `explorer` / `librarian` for facts. Never ask the user for something you can discover.
2. **Grill before writing.** No plan file is written until the frontier is empty and the user confirms shared understanding.
3. **Use the repo's plan convention.** Plans live in `plans/NNN-feature-slug/plan.md`; next number is the highest existing number + 1. Never renumber existing plans.
4. **Do not execute from this skill.** It plans, reviews, and hands off. Code changes belong to `superbuild` or a direct implementation lane.
5. **One writer per file.** Every parallel phase must name a disjoint write scope and a validation owner. No two lanes edit the same file.
6. **Bun is the app runtime.** Generated projects, the `gramstax` CLI, tests, and builds are Bun-only. Do not plan a Node fallback or an alternate app runtime selector.
7. **Never hand-edit generated docs.** `docs-site/reference/**` and `packages/*/docs/{markdown,yaml}` are generated by `bun run build:docs`.
8. **No commit, push, or release unless asked.** Plans may propose a conventional commit message; git operations remain the user's choice.
9. **Fresh evidence only.** A phase is not complete because code "looks right" or because a prior run passed. Run the current command and read the output.
10. **Keep the plan alive.** Every REFINE, RECONCILE, or completed phase updates the plan and its change log.

## Workflow

```
INTAKE → LOAD REPO TRUTH → GRILL (rounds) → EXPLORE → DESIGN → PHASE → VERIFY PLAN → WRITE/HANDOFF
```

1. **Intake.** Capture the request verbatim; classify it as feature, refactor, migration, bug fix, docs, or release work.
2. **Load repo truth.** Read root `AGENTS.md`, the relevant package `AGENTS.md`, `CONTEXT-MAP.md`, the current plan, and any execution report.
3. **Grill.** Build the design tree and ask the whole frontier in rounds. Read `references/grilling.md`.
4. **Explore.** Use read-only agents for pattern discovery, integration points, and technical debt. Read `references/repo-context.md` first.
5. **Design.** Name the changed packages, public APIs, runtime/deploy mode, data/state, tests, docs, and release constraints.
6. **Phase.** Split into independently testable phases with Fibonacci estimates and disjoint write lanes. Read `references/execution-lanes.md`.
7. **Verify the plan.** Check tasks, file paths, TDD steps, DoD, and commands. Read `references/plan-review.md`.
8. **Write or update.** Use `references/plan-template.md` and the mode rules in `references/plan-lifecycle.md`.
9. **Hand off.** Produce a superbuild prompt only after the user confirms the plan is ready.

## Plan Storage

```
plans/
  046-example-feature/
    plan.md                 # required
    plan-2.md               # optional: split when > ~4,000 lines
    execution-report.md     # created by superbuild / resume
```

- Use a zero-padded number and a lowercase hyphenated slug: `046-bun-only-runtime`.
- `plans/` is gitignored. Do not rely on git history; the plan and report are the durable record.
- Existing plans are historical; do not rewrite completed history. Add a new plan or a clearly marked superseding section.

## Status Language

Use one vocabulary everywhere:

`⬜ Not Started` · `🔄 In Progress` · `✅ Complete` · `⏸️ Blocked` · `🔵 Review` · `⏭️ Skipped`

Plan status: `Draft` → `In Review` → `Approved` → `In Progress` → `Complete` (or `Blocked` / `Superseded`).

## Output Contracts

- **CREATE:** plan path, phase table, total estimate, open questions, handoff options.
- **REFINE:** what changed, why, affected phases, change-log entry, new status.
- **REVIEW:** findings ordered by severity; no silent rewrites.
- **RESUME:** last verified phase, current blocker, next action, compact summary.
- **RECONCILE:** planned vs actual, evidence, corrected statuses, follow-up tasks.
- **HANDOFF:** ready/not-ready verdict, plan path, phase, write scopes, validation commands, stop condition.

## Done

A planning session is done when:

- The frontier is empty and the user has confirmed shared understanding.
- Every open question is answered or recorded as a Known Unknown with an owner.
- The plan has exact paths, testable acceptance criteria, per-phase DoD, and disjoint write lanes.
- The verification commands are real Gramstax commands.
- The user has chosen the next action: review, execute now, execute in a fresh session, or stop.

Read `references/plan-lifecycle.md` before editing an existing plan. Read `references/grilling.md` before asking the first question.
