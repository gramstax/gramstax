# Gramstax Superplan

Portable plan lifecycle for developers building **on** Gramstax. It works in:

- an empty or near-empty project that is about to be scaffolded with `create-gramstax`;
- a project generated by `create-gramstax`;
- a standalone app such as `real-projects/*`;
- an existing Bun + TypeScript app that adds `gramstax` as a dependency.

This is the Gramstax front end to the generic `superplan` and `superbuild` skills:

- `superplan` supplies the executable phase structure.
- `grill-me` supplies the design-tree interview method.
- `superbuild` supplies execution discipline when available.
- Gramstax app conventions supply the context: pages, templates, keyboards, config, LMDB, workers, e2e, and deploy.

> **Scope:** this skill plans app-owned files only. Do not edit installed `node_modules/gramstax`, `node_modules/@gramstax/*`, or the framework source. If the project root you are planning is the framework repository itself (root `package.json` plus `packages/gramstax`, `packages/create-gramstax`, `packages/lmdb`, and `packages/worker-thread`), use `gramstax-repo-superplan` instead. A standalone app nested under `real-projects/` is not the framework repo.

## When to Apply

- **Greenfield:** planning a new Gramstax app from an empty/near-empty directory.
- **Adoption:** adding Gramstax to an existing Bun + TypeScript app without scaffolding over it.
- Adding or changing a page, base class, guard, keyboard, or callback flow.
- Adding or changing a template, `g-*` block, filter, or message layout.
- Changing `gramstax.config.ts`, env handling, deploy mode, cache, rate limit, throttle, or status server.
- Adding LMDB schemas, repositories, indexes, migrations, queues, or backups through `@gramstax/lmdb`.
- Adding workers, jobs, RPC, or gateway usage through `@gramstax/worker-thread`.
- Changing the unit/e2e test strategy or the e2e mirror.
- Planning an app-level refactor, upgrade, or multi-phase feature.

Do **not** use this skill for a one-line fix, a known-path edit, or work that already has an approved, current plan. Do that work directly or execute the existing plan.

## Modes

| Mode | Trigger | Output |
| --- | --- | --- |
| **CREATE** | No plan exists | `plans/NNN-feature-slug/plan.md` |
| **REFINE** | App scope, design, task, or verification changes | Minimal plan edits + change-log entry |
| **REVIEW** | Plan needs an audit before execution | Findings table; rewrite only when asked |
| **RESUME** | Work was paused or compacted | Current state, next phase, blockers, resume prompt |
| **RECONCILE** | Implementation drifted from the plan | Corrected statuses, deviations, re-sequenced phases |
| **HANDOFF** | Plan is ready to execute | `superbuild` prompt, or a manual execution checklist |

## Hard Rules

1. **Facts are your job; decisions are the user's.** Read the app, its dependencies, and its docs. Dispatch `explorer` for code facts and `librarian` for framework/version facts. Never ask the user for something you can discover.
2. **Grill before writing.** No plan file is written until the frontier is empty and the user confirms shared understanding.
3. **Plan in the app when it exists.** Use `plans/NNN-feature-slug/plan.md`; next number is the highest existing number + 1. Never renumber existing plans. For greenfield, keep the bootstrap plan in the parent workspace (or write it in the new app after the scaffold) so the plan itself does not make the empty target non-empty.
4. **Do not edit dependencies.** `node_modules`, installed package source, and lockfile internals are read-only. Upgrade, patch, or upstream instead.
5. **Read the project's scripts.** Do not assume monorepo commands. When present, `package.json` is the source of truth for `dev`, `start`, `build`, `typecheck`, `lint`, `test`, and `test:e2e`; for greenfield, use the generated scripts after scaffold.
6. **Load the relevant best-practice skill.** Use `gramstax-best-practices` for pages, templates, keyboards, config, e2e, guards, cache, and deploy. Use `lmdb-best-practices` for `@gramstax/lmdb`/`src/db` work. Use `worker-thread-best-practices` for `@gramstax/worker-thread`/`src/workers`/`src/jobs` work. Record the source in the plan.
7. **One writer per file.** Every parallel phase needs a disjoint write scope and a validation owner.
8. **Bun is the app runtime.** Use Bun for boot, tests, builds, and the Gramstax CLI. Do not plan a Node fallback.
9. **Never hand-edit generated output.** `.gramstax/**` is produced by `gramstax build`; regenerate it instead.
10. **No commit, push, or release unless asked.** The plan may propose a commit message; git operations remain the user's choice.
11. **Fresh evidence only.** A phase is complete when the current command passes and its output has been read.
12. **Keep the plan alive.** Every REFINE, RECONCILE, or completed phase updates the plan and its change log.

## App Context Detection

Before asking questions, classify the project from files:

| Context | Signals | Planning rule |
| --- | --- | --- |
| **Greenfield / empty** | No `package.json`, a shell `package.json` with no app source, or an effectively empty directory; no `gramstax` dependency/config | Read `references/greenfield.md`; plan the `create-gramstax` bootstrap as the first phase |
| **Existing app adopting Gramstax** | `package.json` plus app code, but no `gramstax` dependency or `gramstax.config.ts` | Plan an incremental integration (`bun add gramstax`, config, first page); do not scaffold over it |
| **Generated app** | `gramstax.config.ts`, `src/pages/`, `e2e/`, `package.json` with `gramstax`; scaffold scripts | Follow the generated project's scripts and structure |
| **Standalone app** | Own `.git`, own lockfile, possibly a pinned older `gramstax`; e.g. `real-projects/*` | Do not assume workspace membership; check the installed version |
| **Ecosystem integration** | `@gramstax/lmdb` or `@gramstax/worker-thread` is a dependency, but the project is not a full Gramstax app | Plan the integration surface; read the installed package README/version |
| **Framework repo** | Root `package.json` plus `packages/gramstax`, `packages/create-gramstax`, `packages/lmdb`, `packages/worker-thread` at the project root | Stop; use `gramstax-repo-superplan` |

For a `real-projects` app, inspect its own `package.json`, `gramstax.config.ts`, `src/`, `e2e/`, `test/`, and `plans/` before making any assumption. Do not copy framework-monorepo rules into it.

## Greenfield Bootstrap

When the project is empty, read `references/greenfield.md` and make bootstrap Phase 1:

```bash
bunx create-gramstax@latest my-bot --pm bun --lmdb --worker-thread --biome
```

For a current empty directory, run interactively and submit an empty project name; do **not** pass `.` as the project name. A plan file created in the target directory makes it non-empty, so for a new subdirectory keep the approved plan in the parent until the scaffold exists and then move it under the app's `plans/`. If the target must be the current directory, finish the grill/design first, scaffold interactively, then write the plan inside the new app. In a non-TTY environment, state all three feature flags explicitly.

## Best-Practice Routing

Load the matching skill before designing app behavior:

- `gramstax-best-practices` for pages, templates, keyboards, config, e2e, guards, cache, and deploy.
- `lmdb-best-practices` for `@gramstax/lmdb` / `src/db` / schema / index / migration / backup work.
- `worker-thread-best-practices` for `@gramstax/worker-thread` / `src/workers` / `src/jobs` / RPC / gateway work.

If the app does not have those skills, read their `SKILL.md` from the Gramstax repository or use the installed package README. Record what was consulted in the plan; see `references/best-practices.md`.

## Workflow

```
INTAKE → LOAD APP TRUTH → LOAD BEST PRACTICES → GRILL (rounds) → EXPLORE → DESIGN → PHASE → VERIFY PLAN → WRITE/HANDOFF
```

1. **Intake.** Capture the request verbatim; classify it as greenfield, feature, page, config/deploy, data, worker, test, refactor, upgrade, or docs.
2. **Load app truth.** Read `package.json` when present, `gramstax.config.ts`, `README.md`, any `AGENTS.md`, env variable names from `.env.example`/config/README (never read or plan with secret values), `src/`, `e2e/`, `test/`, and the current plan/report.
3. **Load best practices.** Read `references/best-practices.md` and load the relevant skill(s): `gramstax-best-practices`, `lmdb-best-practices`, `worker-thread-best-practices`.
4. **Grill.** Build the design tree and ask the whole frontier in rounds. Read `references/grilling.md`.
5. **Explore.** Find existing pages, guards, keyboards, data flows, tests, and version constraints. Read `references/app-context.md` first.
6. **Design.** Name the app surface, route flow, template/keyboard behavior, data/state, workers, deploy mode, tests, and dependency constraints.
7. **Phase.** Split into independently testable phases with Fibonacci estimates, disjoint write lanes, and validation owners. Read `references/execution-lanes.md`.
8. **Verify the plan.** Check exact paths, tests, DoD, and real app commands. Read `references/plan-review.md`.
9. **Write or update.** Use `references/plan-template.md` and the mode rules in `references/plan-lifecycle.md`.
10. **Hand off.** Produce a `superbuild` prompt when available; otherwise produce the same phase-by-phase execution checklist for the user's agent.

## Plan Storage

```
plans/
  016-example-feature/
    plan.md                 # required
    plan-2.md               # optional split for a very large plan
    execution-report.md     # created by superbuild / resume
```

- Use a zero-padded number and a lowercase hyphenated slug: `016-checkout-flow`.
- If `plans/` does not exist, create it. If it is gitignored, keep the plan on disk and tell the user it will not be committed.
- `real-projects/production-vip-content-bot` already uses `plans/001-...`; follow the existing number sequence there.
- **Greenfield:** keep the approved plan in the parent while the app directory does not exist; after scaffold, create `plans/` inside the app and move the plan there. If scaffolding into the current empty directory, finish the grill/design first, then write the plan inside the new app. A plan file in the target makes it non-empty. See `references/greenfield.md`.
- Existing plans are historical; do not rewrite completed work. Add a new plan or a marked superseding section.

## Status Language

`⬜ Not Started` · `🔄 In Progress` · `✅ Complete` · `⏸️ Blocked` · `🔵 Review` · `⏭️ Skipped`

Plan status: `Draft` → `In Review` → `Approved` → `In Progress` → `Complete` (or `Blocked` / `Superseded`).

## Output Contracts

- **CREATE:** plan path, context classification, phase table, total estimate, open questions, handoff options.
- **REFINE:** what changed, why, affected phases, change-log entry, new status.
- **REVIEW:** findings ordered by severity; no silent rewrites.
- **RESUME:** last verified phase, current blocker, next action, compact summary.
- **RECONCILE:** planned vs actual, evidence, corrected statuses, follow-up tasks.
- **HANDOFF:** ready/not-ready verdict, plan path, phase, write scopes, validation commands, stop condition.

## Installing This Skill In Your App

Copy this directory into your app's `skills/` directory (or the skill directory your agent uses), keeping `references/`, `CHANGELOG.md`, and `LICENSE`. For full coverage, also copy `gramstax-best-practices`, `lmdb-best-practices`, and `worker-thread-best-practices`; this skill routes to them. Do not copy `gramstax-repo-superplan` into an app; it is only for the framework monorepo.

## Done

A planning session is done when:

- The app context is classified and recorded, including greenfield vs existing app.
- The relevant best-practice skill(s) are recorded as consulted.
- The frontier is empty and the user has confirmed shared understanding.
- Every open question is answered or recorded as a Known Unknown with an owner.
- The plan has exact app paths, testable acceptance criteria, per-phase DoD, and disjoint write lanes.
- The verification commands exist in the app's `package.json` or are valid Bun equivalents.
- The user has chosen the next action: review, execute now, execute in a fresh session, or stop.
