# Gramstax App Context For Planning

This reference is for a project that **consumes** Gramstax, not for the framework repository. Read the app's own files before planning.

## Context Classification

| Context | Signals | Planning implication |
| --- | --- | --- |
| **Greenfield / empty** | No `package.json`, a shell `package.json` with no app source, or an effectively empty directory; no `gramstax` dependency/config | Scaffold first with `create-gramstax`; see `greenfield.md` |
| **Existing app adopting Gramstax** | `package.json` plus app code, but no `gramstax` dependency or `gramstax.config.ts` | Plan an incremental integration (`bun add gramstax`, config, first page); do not scaffold over it |
| **Generated app** | `gramstax.config.ts`, `src/pages/`, `e2e/`, `package.json` with `gramstax`; `create-gramstax` scripts | Use the generated structure and its scripts |
| **Standalone app** | Own `.git` and lockfile; for example `real-projects/production-vip-content-bot` | Do not assume workspace membership; read the pinned version |
| **Ecosystem integration** | `@gramstax/lmdb` or `@gramstax/worker-thread` is a dependency, but there is no full Gramstax app | Plan the integration boundary and package version |
| **Framework repo** | Root `package.json` plus `packages/gramstax`, `packages/create-gramstax`, `packages/lmdb`, `packages/worker-thread` at the project root | Stop; use `gramstax-repo-superplan` |

A project can be both a generated app and a standalone app. The distinctions that matter are: who owns the files, which version of Gramstax is installed, and which scripts actually exist.

## App Layout

A `create-gramstax` project typically looks like this:

```text
gramstax.config.ts     # token, deploy mode, caches, runtime tuning
src/
  base/                # PageBase, GuardBase, shared page behavior
  blocks/              # reusable keyboard/template blocks
  core/                # BotCore, CtxCore, services wiring
  db/                  # LMDB schemas and repositories (optional)
  guards/              # route guards and input validation
  helpers/             # logging, formatting, domain helpers
  pages/               # one file or folder per route
  types/               # shared types grouped by domain
  utils/               # pure generic utilities
  workers/             # worker-thread jobs (optional)
e2e/                   # in-process user journeys; mirrors src/pages/ + COVERAGE.md ledger
test/                  # unit tests for pure logic
scripts/               # e2e mirror check + handler ledger audit + structure generator
plans/                 # implementation plans, when the project uses them
.gramstax/             # generated by `gramstax build`; never hand-edit
```

A standalone app may differ. `real-projects/production-vip-content-bot`, for example, has `src/jobs/` instead of `src/workers/`, a second bot entry, and its own `plans/001-...` sequence. Detect the real layout; do not copy the generated template blindly.

## Read This First

| If the plan touches… | Read |
| --- | --- |
| Pages, callbacks, navigation, free text | `src/pages/**`, `src/base/**`, `src/guards/**`, `e2e/**`; `gramstax-best-practices` |
| Templates, `g-*` blocks, filters, keyboards | Relevant page, `src/blocks/**`, `src/base/**`; `gramstax-best-practices` |
| Boot, env, caches, deploy | `gramstax.config.ts`, `src/env.ts` or equivalent, env docs (`.env.example` if present), `README.md`; `gramstax-best-practices` |
| LMDB | `src/db/**`, `test/**` DB tests, installed `@gramstax/lmdb` README; `lmdb-best-practices` |
| Workers/jobs | `src/workers/**` or `src/jobs/**`, `test/**`, installed `@gramstax/worker-thread` README; `worker-thread-best-practices` |
| Generated output | `.gramstax/**` is read-only output; change the source and rebuild |
| App docs | `README.md`, `AGENTS.md` if present, `docs/**` if present |
| Greenfield scaffold | `greenfield.md` |

If the app has no `AGENTS.md`, do not invent one. Use `README.md`, `package.json`, `gramstax.config.ts`, and the source. For greenfield, use `greenfield.md` first.

## Scripts Are the Source of Truth

Read `package.json` before naming a command. Generated projects typically expose:

| Script | Typical command |
| --- | --- |
| `dev` | `gramstax start --watch` |
| `start` | `gramstax start` |
| `build:gramstax` | `gramstax build` |
| `typecheck` | `tsc --noEmit` |
| `lint` | `biome lint` or `biome check` |
| `test` | `bun test test/` |
| `test:e2e` | `bun test e2e/` |
| `test:e2e:check` | `bun run scripts/check-e2e-mirror.ts && bun run scripts/check-e2e-handlers.ts` |
| `test:all` | coverage checks, then both suites |

A standalone app may use `build`, `lint:fix`, or a different test command. Use the names that exist. If a script is missing, use a direct Bun equivalent only after saying so in the plan.

## Version and Dependency Rules

- `package.json` is the version truth when present. Record the `gramstax`, `@gramstax/lmdb`, and `@gramstax/worker-thread` versions in the plan.
- For greenfield, record the `create-gramstax` command and the versions it generates. There is no installed app version yet.
- Do not assume the app uses the latest framework API. Read the installed package version and its README before planning a call that may have changed.
- `node_modules` is read-only. Never plan edits there. If the app must change framework behavior, choose one of:
  - upgrade the dependency;
  - use a public extension point;
  - patch/upstream the framework;
  - change the app design.
- `real-projects/production-vip-content-bot` may pin older majors. A plan for that app must use its pinned API, not the current `main` API.
- `@gramstax/lmdb` and `@gramstax/worker-thread` are separate packages. Their own multi-runtime support does not make a Gramstax app Node-compatible.

## Pages and Templates

- A page is usually a class under `src/pages/` with `show` / `process` steps, route handlers, keyboards, and session state.
- `src/base/` contains project-specific base classes; changes there can affect many pages.
- `src/guards/` controls access and input; a guard change needs route-level tests.
- `src/blocks/` contains reusable keyboard/template builders; one block change can affect many pages.
- E2E tests under `e2e/` should mirror the page tree, and `e2e/COVERAGE.md` is the handler ledger. If you add or rename a page or handler, plan the mirror test and the ledger row, then run `bun run test:e2e:check` (mirror + ledger audit).
- `gramstax build` freezes pages into `.gramstax/`. It is generated output; do not hand-edit it.

## Data and Workers

**LMDB (`@gramstax/lmdb`)**

- Read `src/db/schema`, `src/db/repositories`, and the app's DB tests.
- Plan schema, key, index, transaction, migration, TTL, queue, and backup changes explicitly.
- A schema change needs a migration/compatibility note and a restart test.
- Do not change an index or key shape without checking existing data and rollback.

**Worker thread (`@gramstax/worker-thread`)**

- Read `src/workers/**` or `src/jobs/**`, the launch/init pair, and lifecycle tests.
- Plan worker start/stop, RPC method signatures, timeout/retry, gateway path, and shutdown behavior.
- A worker change needs a test for startup failure and shutdown, not just the happy path.

## Deploy and Operations

- `deploy` is configured in `gramstax.config.ts`: `polling`, `webhook`, `serverless`, `raw`, or `test`.
- `.env*` files are loaded by `gramstax start` / `gramstax build`; shell values win.
- Webhook/status uses `Bun.serve`; serverless emits a target-specific entry under `.gramstax/server/`.
- `deploy: "raw"` is a bare grammY bot: no pages, templates, or Gramstax routing.
- Plans that touch secrets, tokens, webhook URLs, or status-server exposure need a security note.
- Never add a real token to `.env.example`, docs, or a plan.

## Quality Commands

Use the narrowest app command that proves the change, then the full app gate:

| Surface | Command |
| --- | --- |
| Typecheck | `bun run typecheck` |
| Lint | `bun run lint` |
| Unit tests | `bun run test` |
| E2E tests | `bun run test:e2e` |
| E2E coverage gate | `bun run test:e2e:check` |
| All tests | `bun run test:all` |
| Build | `bun run build:gramstax` or `bun run build` |
| CLI smoke | `bun run start -- --help` or `bunx gramstax start --help` |
| Whitespace/conflicts | `git diff --check` |

If a script is absent, read the app's actual tooling and use an equivalent direct command. Do not import monorepo scripts such as `bun run ci:check` into an app plan.

## Planning Checklist

- Which app context is this: greenfield, generated, standalone, or ecosystem integration?
- Which version of `gramstax` / `@gramstax/lmdb` / `@gramstax/worker-thread` is installed, or which scaffold will produce it?
- Which best-practice skill sections apply?
- Which files may change, and which are generated or vendored?
- Which page/route and e2e mirror are affected?
- Which config/deploy mode is active?
- Which data or worker lifecycle changes?
- Which scripts prove the change?
- Does the plan avoid editing `node_modules` and `.gramstax/`?
